# 验证范围

本仓库拆分自已在物理H1上开发的QQ音乐0.1.11。应用C源码保持不变；
构建拆除无关工作区依赖，改为固定SDK子模块、可配置工具链、稳定归档顺序和路径前缀映射。
发布的确切BDA必须从干净检出构建并经下面的实际MIPS测试，不能把旧工作区产物直接当CI输出。
各次构建的精确SHA-256在Release `SHA256SUMS.txt` 和构建信息中。

## 自动化检查

- 正式/调试BDA头、标题、分类、资源、payload、入口及格式校验。
- `test_h1_qqmusic_modes.py`：真实链接MIPS的1～12首队列策略、真实AAC EOF自动切歌、后台视图、
  顺序末尾停止、列表/单曲循环、随机历史、按键/触屏模式切换、退出配置保存和重启恢复、权限跳过、暂停/定位/尾部排空。
- `test_h1_qqmusic_buffer.py`：真实AAC储备>=49152B、无空READ、BUSY时PCM回调、三次合法脚本游标欠载后恢复，
  不重置AAC，不用墙钟伪造媒体进度；错误响应停止、保留计数、堆/句柄清理。
- `test_h1_qqmusic_navigation.py`：后台列表/首页/翻页/搜索、正在播放保持同一会话、账号权限验证/清理、
  原生输入暂存与恢复、触屏拖动。网络和扫码账户只使用合成测试数据。
- `test_h1_qqmusic_stream.py`：原C网络层、线协议及服务端；合法700ms模拟CDN延迟下预开下一Range，
  两任务上限、BUSY、跳转、退出和故障释放。模型时间不代表物理USB/无线速度。

这些是脚本固件/GUI/DAC边界下的实际MIPS程序执行，AAC由PC PyAV真实解码；
不是完整BBK固件模拟器，也不是ESP芯片硬件测试。CI报告与运行截图随对应Actions artifacts提供。

## 已有物理H1证据及边界

原工作区0.1.9的用户反馈：播放《LOVE OPTIONS》1～2分钟、退列表翻页再回正在播放“没卡”；
韩文标题和歌词“正常了”。扫码后已登录标签、可播放标签、返回同一首也有早期反馈。
未将一次账号方式的反馈扩大到QQ/微信两种均完成真机验收。

0.1.10用户反馈仍有约90秒短停：物理保留数据为预取4次/提升4次、最大提升读取18ms，
但原生PCM欠载3次/恢复2次。115990次PCM READ中72542次为空，故0.1.11增加现有ESP PCM环的提前解码储备。
严格原生媒体时钟保持不变，ESP仍为0.4.4，不往ESP添加站点或账号逻辑。

原工作区0.1.11已在物理H1安装，设备整文件CRC通过，运行载入前256B一致，480×272首页截图已检查；
观察结束后释放H1Debug，ESP INFO显示USB和Wi-Fi true、无发送/CRC错误。其BDA SHA256为
`20e56efaa8918adb6bddf5f1603c3ee87ed10763b86f5259357777d49f7aa776`。
这是原工作区产物的记录；独立构建的路径/归档规范调整会改变链接布局，不能把该哈希当作Release哈希。

**仍待最终实体试听：0.1.11连续>=3分钟、约90秒是否短停，以及自然切歌/四模式。**
没有据模型检查写成“所有曲目长稳”，也未将待机HTTP心跳当成试听证据。

## 无商业数据

仓库运行截图只包含自制合成音频/封面及测试文本；不分发真实歌曲、用户Cookie、扫码令牌、
账号文件、Wi-Fi密码、BBK固件、NAND或其他应用的二进制。测试不会打开串口或更改用户账号。
